# fixtures

Small, committed inputs and expected outputs that every pipeline gate runs
against. Nothing here is production data.

## golden/synthetic/

Expected Stage-1 + dedup output for the synthetic bundle generated by
`packages/pipeline/tests/synthetic_bundle.py` (five revisions over two pages
that exercise every reference kind the extractor knows). The test
`packages/pipeline/tests/test_stage1_golden.py` regenerates the bundle, runs
`wcd extract` and `wcd dedup`, and compares every table set-wise with these
files. After an intentional pipeline change, regenerate with
`UPDATE_GOLDEN=1 uv run pytest packages/pipeline/tests/test_stage1_golden.py`
and review the diff before committing.

## golden/stage0/

`fixture.parquet` is the metadata RevisionChest writes (`--parquet`) for the
mwdump test dump `rust/revisionchest/crates/mwdump/tests/fixtures/fixture.xml.bz2`
(4 pages, 9 revisions). `packages/pipeline/tests/test_postgres_integration.py`
feeds it to `wcd stage0-load` and checks the Postgres rows, the `revisions`
Parquet partitions and the Stage-0 gate; with `REVISIONCHEST_BIN` set it also
regenerates the file from the dump and requires equality. Regenerate after an
intentional metadata change with
`RevisionChest build …/fixture.xml.bz2 -o /tmp/rc --parquet fixtures/golden/stage0/fixture.parquet`.

## shards/

The sampled test-article subset of English Wikipedia, with each page's **full
revision history** up to a fixed cutoff. It serves three purposes at once:
matching-quality evaluation for the ported UVA code, a scale and performance
rehearsal input, and the API/frontend fixture database. It comes in two
nested tiers, recorded in the `tier` column of `pages.tsv`:

* **ci** — about 70 pages with at most 1,500 revisions each, small enough to
  run on every build and to hold golden outputs (`golden/ci/`).
* **rehearsal** — every selected page (about 400), including a few very long
  histories; for performance runs, not goldens.

The selection centres on WikiProject Medicine and WikiProject Military
history (dense citation networks: journal citations with PMID/DOI on one
side, `{{sfn}}` shortened footnotes and ISBN book citations on the other),
taken as clusters of linked articles so that cross-page source matching has
shared sources to find, plus assessment-class strata, pages in both projects,
random articles, Cite-error and list-defined-reference pages, and hand-picked
edge cases. The criteria are documented at the top of
`scripts/select_fixture_pages.py`.

Histories come from the Action API rather than from dump chunks:
`scripts/export_history.py` fetches each page's revisions up to the cutoff
and writes export-0.11 XML. That approximates a dump taken at the cutoff;
the differences (revisions deleted since the cutoff are missing, revisions
history-merged since are present, titles are current) are listed in its
docstring. Because the API's answers change over time, **`pages.tsv` and
the exported XML are the record**, not a re-run of the scripts.

How it is built (needs `CONTACT_EMAIL` in `.env`; run from the repository root):

1. Select the pages. Choose the cutoff once (e.g. the date of the dump the
   full build uses) and keep it:

   ```
   uv run python scripts/select_fixture_pages.py --cutoff 2026-10-01T00:00:00Z
   ```

   This writes `fixtures/pages.tsv` (with the wiki and cutoff in its header),
   `fixtures/pages.txt` and `fixtures/pages.ci.txt`. Optional:
   `--seed-page "Medicine=<title>"` to choose cluster seeds instead of drawing
   them, and `--extra fixtures/fixture_extra.tsv` for hand-picked pages
   (`title<TAB>reason[<TAB>ci]` per line). The projects' assessed-page lists
   are cached in `data/fixture/candidates.tsv.gz`; delete it to refetch.
   Review the summary it prints (pages and approximate revisions per tier).

2. Export the histories (resumable; re-run after an interruption):

   ```
   uv run python scripts/export_history.py fetch
   uv run python scripts/export_history.py write
   ```

   This writes `data/fixture/fixture.xml.bz2` (all pages),
   `data/fixture/fixture-ci.xml.bz2` and `data/fixture/export.json` (per-page
   counts, pages left out and why, SHA-256 of both files).

3. Build the bundles and metadata for each tier:

   ```
   RevisionChest build data/fixture/fixture-ci.xml.bz2 -o fixtures/shards/ci \
       --parquet fixtures/shards/ci/meta.parquet --domain en.wikipedia.org
   RevisionChest build data/fixture/fixture.xml.bz2 -o data/fixture/shards/rehearsal \
       --parquet data/fixture/shards/rehearsal/meta.parquet --domain en.wikipedia.org
   ```

4. Run the pipeline on the ci shard and record its goldens under
   `golden/ci/` with `packages/pipeline/tests/test_fixture_ci.py` (see
   `golden/ci/` below).

Commit `pages.tsv`, `pages*.txt`, `export.json` and the ci shard. The
rehearsal bundle stays outside git; keep it with its `export.json` hashes.
To run the rehearsal tier, split its single bundle so Stage 1 can use every
core, then run the driver:

```
uv run python scripts/split_bundle.py data/fixture/shards/rehearsal/fixture.xml.mwrev.zst -n 8 -o data/fixture/shards/rehearsal/pieces
DATABASE_URL=postgresql://…/wcd_rehearsal PARQUET_DIR=data/rehearsal/parquet \
    scripts/run_pipeline.sh data/fixture/shards/rehearsal/pieces data/fixture/shards/rehearsal/meta.parquet en.wikipedia.org 8
```

After an extractor or normalizer change, Stage 1's output is stale: remove
the run's staging directory (`data/rehearsal/staging` here — `extract-all`
would otherwise skip every piece marked `DONE`) and run the driver again; it
recreates the schema and redoes everything from Stage 0.

`wcd fixture-dump` remains for cutting the same page list out of real
`pages-meta-history` dumps (it reads `pages.txt`); note that it holds each
`<page>` element in memory until the page ends.

## golden/ci/

Every output of the full pipeline (Stages 0–8) on `shards/ci/`: one file per
Postgres table and per Parquet dataset, in a canonical form (load-order
surrogate keys replaced by natural keys, floats rounded, JSON key-sorted), plus
`summary.json` with row counts, fixture coverage and step timings.
Snapshots over 50,000 rows are stored as per-page digests (`*.fp.parquet`).
`packages/pipeline/tests/test_fixture_ci.py` runs every `wcd` command in
order with its gate, checks coverage, and compares each output with these
files. It needs a scratch Postgres database (its `public` schema is dropped):

```
export WCD_TEST_DATABASE_URL=postgresql://user:pass@127.0.0.1:5432/wcd_fixture_test
UPDATE_GOLDEN=1 uv run pytest packages/pipeline/tests/test_fixture_ci.py -v   # record
uv run pytest packages/pipeline/tests/test_fixture_ci.py -v                   # compare
```

Re-record after an intentional pipeline change and review the diff of
`summary.json` before committing. Extraction dominates the run (about 14
minutes on one core: the shard is a single bundle, so `--jobs` does not help
Stage 1); every other stage takes seconds.

## sample/ (extractor comparison sample)

Manifests for the Python-vs-Rust extractor comparison: one TSV per wiki
(`wiki, rev_id, page_id, ns, title, stratum, detail`) plus `sample.json` with
the parameters and per-stratum counts. Wikis: en, fr, de, it, rm, zh, ar, sr.
The TSVs are the reproducible record; random sampling and recent changes are
not repeatable, so regenerate only on purpose.

`scripts/sample_revisions.py` builds it and documents the strata (random,
Special:LongPages, linter errors, tracking categories, reverted edits):

1. `uv run python scripts/sample_revisions.py probe` checks every source on
   every wiki (needs `CONTACT_EMAIL` in `.env`).
2. `… manifest --total 70000` writes `fixtures/sample/`.
3. `… fetch` downloads the revisions into `data/sample/` (git-ignored) as
   `<wiki>.xml.bz2` in export-0.11 format. It is resumable.
4. `… mutate --variants 1` writes `<wiki>.mutated.xml.bz2`: damaged copies
   with synthetic revision ids (`10_000_000_000 + rev_id * 10 + variant`)
   and a `<wiki>.mutations.tsv` log.
5. `RevisionChest build data/sample/<wiki>.xml.bz2 -o data/sample/bundles --no-db`
   turns either file into the bundle both extractors read.
